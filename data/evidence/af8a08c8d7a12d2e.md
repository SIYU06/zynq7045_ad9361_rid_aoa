## 3. 系统结构与数据链

```text
A/B：AD9361 双 RX → FPGA / OpenWiFi → Linux
  ├─ 18771：监测、802.11 帧、RID、信源、资源、接收角色
  └─ 18788：目标 MAC 调度、同源双 RX IQ、窗口与原始 IQ
                       ↓ 以太网 HTTP
PC：serve.py + RIDFleet / SignalBridge / ProcessingPipeline / DOABridge
                       ↓ 同源 /api/*
浏览器：index.html → workspace.js → 地图、测向、布站、记录等视图
```

PC 服务使用 Python 标准库 `ThreadingHTTPServer`，同时提供静态文件和 API；后台线程负责轮询、角色确认、信源识别、IQ 调度和测向。前端为原生 HTML/CSS/JavaScript ES modules，地图库 Leaflet 本地保存。

当前完整链按“检测采集 → 特征识别 → 身份解析 → 测向定位”处理。默认 B 承担完整信源检测和身份解析，A 保留独立双 RX 测向与必要的目标帧关联；A/B 都参与测向。角色切换会真实调用板端控制，并等待确认，部分失败会显示失败或回滚；列表筛选只改变显示。

RID 与图传候选通过证据分类进入目标 IQ 调度。IQ 对应 MAC、频点、会话、TSF、FCS、哈希及 LTF 位置检查；两站只有满足同源同帧、新鲜度与几何条件才可形成交汇候选。广播 GPS 位置与独立 DOA 位置分开。当前 OFDM LTF 测向不能直接用于仅 DSSS 的信源。
