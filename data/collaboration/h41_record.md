# AoA全链路优先与双站地图联调提示

> 本文件供用户审阅修改。此次只写提示词，不启动采集、不操作开发板、不修改地面站代码。用户后续明确说“执行”后，再按本文件推进。用户口述的“AV角度/链路”，本文按AoA/DOA来向估计理解。

## 一、本轮调整后的主线

**先打通真实链路，再优化精度：单站0°/右移/左移响应 → 单站角度进入现有地图 → 第二台平台接入 → 双站方位线及交汇点进入地图 → 精度、稳定性和多目标能力优化。**

用户已接受当前精度作为联调起点。此前“相位标准差≤3°才允许继续”的规定不再作为这一阶段的阻断条件；3.123°等实测结果照实保存，作为后续优化基线。3°是先前设定的相位重复性指标，不能直接等同于最终角度误差。

此前 [17.21相位稳定性排查提示](h40_record.md) 中“先查稳定性、零点全过门槛再接地图”的推进顺序，按用户本次要求调整为本文件的链路优先顺序。历史报告不改写为通过，不重新宣称精度达标；也不要再因略超3°而停下全部联调、反复要求用户重新标定。

本阶段把“数据能传到地图”“角度是否随信源方向变化”“角度绝对精度”分别记录。方向响应暂不理想时，保留实测并继续完成能独立开展的传输、界面和第二站软件适配，不把接口已连通写成测角已正确。

## 二、已有条件与当前限制

- 当前电脑只连接第一台软件无线电平台，记为站A；第二台尚未接入。一个平台的RX1、RX2共同组成一个双天线测向站，不能把它们当成两个定位站。
- 站A为XC7Z045＋AD9361，双接收天线竖直平行，中心间距5.9 cm；每路约20 cm SMA馈线。直接板端接口间距约1.5 cm不是当前阵列基线。保持现有安装，移动信源时不牵动馈线。
- 最近现场为室外露台，参考ESP32约在阵列正前方1 m，电脑约2 m；用户确认最新静置采样时设备未动、无人靠近。执行前核对当前摆放是否仍相同，不把历史状态当成永远不变。
- 当前信道6、2437 MHz。参考ESP32 MAC为 `mac_aa98f353b5`，RID为 `RIDTEST-ESP32S3-0001`。OpenWiFi经天线真实接收、RID解析和Web地面站已有基础。
- `capture_freshness.py` 已部署：FIFO清空读回、阶段TSF界限、时戳递增、重复IQ拒绝；丢弃窗与拒绝原因保存，PC端可独立核验。43项软件检查通过；最新90个测量窗及9个丢弃窗全部通过新鲜度与完整来源关联。
- 最新三批相位标准差0.347°、3.123°、0.894°；候选偏置134.134399°仅属于当时会话。旧偏置159.7879257°和已结束会话的偏置都不能直接套到新会话。
- 先读 [17.13执行报告](h39_record.md) 和 [17.06缓存核查](h38_record.md)，优先复用已有软件，不重做SD、内核、FPGA、DTB或ESP32固件。

## 三、第一步：先测站A的零点、右移和左移

### 1. 采集约定

使用本轮新RF会话和当前合适的固定增益对；10/7 dB作为已有候选，先检查电平和削顶，不盲目照旧增益补偿。整轮保持同一频率、同一增益会话、天线/馈线/电脑位置，不在不同方向重新归零。

信源正前方位置作本轮零点。可用首20个来源与新鲜度核验合格窗建立临时参考，随后冻结；零点留出窗及后续所有位置都用同一个偏置。三度相位指标只记录，不再触发“停止整轮”。

建议顺序如下，每个位置目标30个有效窗口；采样不足时如实记录，不伪造补齐：

| 顺序 | 位置 | 操作与目的 |
|---|---|---|
| 1 | 原正前方0° | 采30窗，其中前20窗建立本轮临时参考、后10窗留出 |
| 2 | 右侧 | 从开发板一侧面向信源，沿两天线连线方向右移；检查角度变化与符号 |
| 3 | 返回原0° | 保持原偏置，检查能否回到原附近，记录残差 |
| 4 | 左侧 | 从原零点沿天线连线向左移；检查与右侧的响应差异 |
| 5 | 再返回0° | 记录最后回程，不再次训练零点 |

前向距离D约1 m时，左右横移约20 cm便于操作，名义角约±11.3°；若继续用17.6 cm，则名义约±10°。执行时选择一种便于固定的偏移量并记录实际D、x和摆放误差，使用 `atan(x/D)`计算名义角，不要求用户达到精密转台水平。

每次只通知用户完成本步移动，明确回复“已放好/已恢复”后再采，不把一般“好的”当作完成。信源用稳定支撑，源高度与天线朝向尽量保持一致。无需现在购买功分器或先完成全部硬件精度排查。

### 2. 如何判断这一阶段结果

主要观察零点附近有输出、右移与左移能产生可辨认的方向变化、回程有实测记录。若原始相位约定与用户左右相反，可根据已知方向确定一次二值符号，之后固定；不拟合任意比例把结果凑成目标角。

报告每位置的名义角、实测角均值/中位数、离散程度、有效窗数和回零残差。明确“有角度响应”“幅度偏小/偏大”“方向相反”“响应尚不明显”等实际状态。暂不以绝对误差或3°相位标准差阻断地图接入。

数据真实性检查仍保留：旧数据/重复数据/错配来源、明显削顶、DMA错误或缺少有效标定状态时，不作为有效测向值输出；在界面展示原因并让其他独立链路工作继续。不要将“允许精度待优化”解释为允许使用无效数据。

## 四、第二步：把站A真实角度送到现有Web地图

### 1. 复用现有平台

继续使用 `rid_receiver/ground_station/`，已有 `data.js` 的 `ingestDOA()`、`app.js` 的测向站/方位线/交汇点绘图，以及现有18770本地服务和RID桥接。

当前核对的 `serve.py` 有真实RID接口，尚不能据此认定真实DOA后端和持续推送已接好。执行时补齐“板端新IQ → 相位/相对角计算 → 以太网传输/PC接收 → DOA观测汇总 → 浏览器持续更新”的缺口。可扩展现有服务的 `/api/doa` 和前端轮询，或采用适合已有结构的等效接口；不要另建一套无关地图。

串口可以用于板端控制和调试；用于测角的原始信号必须来自天线与双RX采样，不能用ESP32串口输出、RID航向或RID坐标反算角度来替代DOA。

### 2. 相对角与地图朝向

先在界面明确显示“相对阵列正前方角”，约定正右、负左。地图需要全局方位时，另外配置站A的阵列正前方朝向：真北0°、顺时针。

在左右符号已核对的前提下，地图方位为 `wrap360(站点朝向 + 相对角)`。不能只做了零点参考就把相对0°画成真北0°。真实北向尚未确定时，先显示相对角或明确标记为用户设定朝向的联调射线。

站点坐标和朝向单独配置，不能自动把电脑位置当作接收阵列位置；也不能将浏览器约90 m误差的位置当作米级试验真值。近距离先用尺量相对位置和统一场地参考方向；需要落在地图上时再配置锚点，并保留锚点/朝向来源与不确定性。

### 3. 地图和数据状态

只有站A时，显示站A标记、实时相对角、配置朝向后的方位线和观测更新时间；单站只产生方向，不凭一条线生成目标距离或交汇点。近场方位线长度可配置，适合当前米级测试，不沿用固定4.5 km线段影响观察。

允许真实但精度未验收的角度进入“联调观测”显示，标记“实测／精度待优化”。与原先正式验收状态分开，不能因 `production_bearing_enabled=false` 就永远拒绝联调显示，也不能为了显示而把它改成已完成精度验收。

真实联调仍应使用真实数据标识，例如现有外部模式的 `demo=false`；模拟、回放、真实但未验收三者保持可区分。至少保留站点ID、观测时间/数据年龄、相对角、地图方位、来源、标定会话和质量状态。断流或过期后射线变灰/隐藏并标注末次观测，不让旧角度一直冒充实时。

RID广播位置与DOA交汇位置分别保留来源。RID位置不可用时仍能看测向线；RID位置可用时可作对照，不能暗中用它拉正DOA射线。

## 五、第三步：接入第二台平台，形成双站链路

站A角度和地图接入推进后，再通知用户接第二台平台，记为站B；目前不假设站B已在线、串口号、网口地址或软件版本与A一致。

1. 核对站B供电、串口、网络、双RX天线和馈线是否齐备。真正的同时双站需要两台平台各自有双路接收天线，不能把现有同一对天线或同一批IQ复制成两站。
2. 先盘点电脑网络接口和现场交换机/网线条件，确定两站怎样同时联网。区分串口号、MAC和IP；如两板镜像配置相同导致地址冲突，给两站配置独立标识和地址，不覆盖已工作的站A配置。
3. 在站B复用站A已经验证的数据新鲜度、采集、临时参考与角度上报流程。分别保存间距、增益、安装朝向和标定会话，不能复制站A相位偏置给B。
4. 两站先观察同一个静止参考信源，分别有真实角度进入地图后再计算交汇。联调可用已知MAC/RID关联参考源，但正式全信道监测不得因此改成白名单。
5. 两站原始硬件TSF起点各自独立，不能直接比较数值。先以PC接收时间和数据年龄建立可配置的观测配对窗口，记录延迟及两站观测时间差；后续移动目标再优化时钟与同步。不可将“最后一次A角”和很久以前的B角随意配对。

站B尚未接入期间可以先完成双站数据结构、配置入口、交汇计算和明确标识的模拟/回放测试；保留“待第二站实测”状态，不能声称真实双站已完成。

## 六、第四步：双站交汇进入地图

先配置两站位置和阵列朝向。米级联调优先使用实测局部坐标，例如站A作原点，量出站B相对位置和朝向；计算在局部平面中进行，再通过同一个地图锚点转换为经纬度。两站不能各自使用相差几十米的浏览器位置当作真实基线。

用同一目标的两条前向方位射线求交，输出“试验交汇点”并持续更新。第一版先展示两站标记、两条射线和交汇点，不急于叠加复杂滤波。前后镜像通过本次已知前半空间约定处理，不能宣称两根天线已经解决全空间消歧。

射线近乎平行、交点在站点背后、观测过期/缺站、来源无法可靠配对时，显示两站已有观测和不能交汇的原因，不硬凑定位点。精度未验收的交点允许用于联调展示，但不能从单站相位标准差直接虚构以米为单位的置信半径。

目标移动后，检查两站射线和交汇点能否随观测变化；轨迹只累计真实有效交汇结果，并记录缺口。仅有RID轨迹或模拟交汇更新不算真实双站链路打通。

## 七、本阶段交付与后续优化

| 阶段 | 本阶段完成证据 |
|---|---|
| 站A方向响应 | 0、右、回零、左、回零的真实IQ和角度记录，变化及偏差如实列出 |
| 站A地图链路 | 实时采集产生角度，通过服务持续进入现有地图；方位线随输入更新，过期可识别 |
| 站B接入 | 两台真实设备各自有新观测，身份、网络和标定不串用 |
| 双站地图链路 | 同一目标的两条真实方位线及可计算时的试验交汇点，实测结果与模拟明确区分 |
| 证据和接续 | 原始IQ、PCAP、完整来源/新鲜度关联、站点几何、配置、时间、标定版本、日志和报告 |

链路打通之后再集中做精度：机械标记与馈线固定、通道幅相/跟踪、接口同步和标定稳定性、LTF/子载波与通用突发算法对比、多角度多距离统计、双站基线与朝向误差、时序关联与滤波。MUSIC等算法先作为可比较方案，不因名称先进就替换已能贯通的主线。

最终系统仍面向无人机/FPV及未知信号的被动监测。当前先用可核验参考源打通链路，不把“未解码”直接当作黑飞，不承诺当前OFDM分支覆盖BLE、DSSS或所有FPV；宽频段和多协议扩展放到本阶段之后。

## 八、给后续执行助手的直接指令

按本文件先贯通AoA/DOA到现有Web地图，再优化精度。用户明确接受目前约3.12°相位标准差作为联调起点，不再用旧3°门槛阻止左右响应测试和地图接入。保持数据真实性、新鲜度、异常恢复和来源标识，不把放行联调写成精度验收通过。

当前只有站A在线。先用新的临时零点参考做0→右→0→左→0，同一会话冻结偏置，输出真实相对角并接现有地图。地图已有绘图入口，优先补真实DOA传输/汇总，不新建无关平台。只有必要物理移动和第二站接线才请求用户配合；其余软件工作自主推进。无需为每个已授权步骤重复询问方案许可。

站B接入后核对独立网络标识、各站双路天线及独立标定，使用实测站间几何和同一目标的有时效观测计算交汇。站B未接前继续完成可独立进行的接口和交汇测试，模拟必须明确标识。缺乏真实第二站时不宣布真实双站成功，单站也不伪造距离。

每轮将执行报告及接续提示写到“提示词”文件夹，使用 `MM.dd_HH.mm简要标题.md`，日期与时间之间为下划线。优先读最新报告，复用已有成果；用户批准本文件后执行，当前文档撰写轮次到此为止。
