# 非RID图传识别与AOA实测报告

时间：2026-11-02 14:18，后续收尾状态见证据目录中的验收文件。

## 1. 本轮结论

已实现并实际触发这条分支：**空口检测 → 图传特征识别 → 无RID，跳过身份解析 → 同源双RX相位／AOA诊断**。

两站均实际接收到了此前测试的无人机图传，数据来自接收天线、AD9361、FPGA Wi-Fi解码和双通道IQ，经以太网进入PC。串口用于部署与状态检查，没有从无人机、遥控器或ESP32串口获取目标内容。

**本轮没有获得有效的双站交汇坐标，也没有完成角度精度验收。** 当前显示的软件几何仍是每站6.0厘米、站距2.8米；用户已说明实物尺寸尚未调整，新的通道相位偏置和站体朝向也未标定。尺寸摆对后仍需标定，不能认为修改间距数值就自动准确。

板端系统日历时间不一致，PCAP内的绝对日期不能用于两站配对。本轮使用PC接收时间、板端单调时间计算新鲜度，并在各站内部用硬件TSF关联IQ与该站的解码包。

## 3. 修复的三个实际问题

### 3.1 不能把一次协商端口写死

首次图传已经收到了，但历史规则把接收端口限定为49870，而本次开机协商为49869，因此没有进入测向。已修正为动态接收端口，并仍要求实测私有UDP分片结构、发送方向、连续多包和不同图像序号。没有用历史MAC白名单作为识别条件。

普通大流量UDP仍不足以确定无人机。现阶段给出“Wi-Fi图传候选／无人机待核验”；本次开关机对照支持它与这台测试无人机有关，不推广为所有无人机的通用指纹。新增JPEG头结构解析，可显示图像宽高；未解密受保护Wi-Fi载荷。

### 3.2 HT图传不能沿用ESP32旧帧时序

旧验证基线是ESP32的legacy OFDM帧。该无人机使用HT图传，FPGA接收状态机中包头有效信号产生的位置不同。若套用旧19微秒时序，会把真实IQ全部拒绝。

已增加Radiotap MCS元数据解析，并将当前硬件上的HT20短GI、MCS 0～5时序单独处理：从LTF位置预测包头锁存时间，偏移30.5微秒、容差1.5微秒。该配置限定当前内核 `5.15.0-175919-g427c94e8faa5-openwifi-rx1`、20 MS/s双IQ、1536点预触发。MCS 6/7、长GI、HT40及其他PHY未取得同等验证，保持拒绝而不是就近匹配。

同时将LTF搜索限制在触发前，避免选中同一IQ窗口中后续别的包的更强前导。保留完整MAC、FCS、原始帧SHA256、IQ大小与SHA256、新鲜度、LTF质量及TSF时序校验。

Radiotap位字段含义依据[官方MCS字段定义](https://radiotap.org/fields/MCS.html)。30.5微秒属于本工程实际接收机时序测量，不是Wi-Fi标准规定的通用常数。

### 3.3 重复空数据帧不能伪装成同一次发射

无人机会大量重复发送24字节的NULL帧，序列字段也可能不变，其完整内容和SHA256会反复相同。此类帧可以证明当前MAC的单站相位，却不能仅凭两站哈希一致就确认同一次发射。

已增加 `framePairingEligible`，NULL帧不参与双站交汇；有载荷的数据帧或有时间字段的有效广播帧才进入配对候选。网页保留单站方向观察，等待可区分的双站数据帧，不生成虚假定位点。

第三轮旧实时快照曾计出50次相同NULL内容快照、1种哈希。最终验收不把它们计为有效同一次发射配对。第二轮保存数据中有1种可配对数据帧哈希，第三轮保存的两站IQ中没有共同的合格数据帧哈希。

## 4. 测向结果与准确性边界

两轮分别保存A/B各16组原始双通道IQ，共64组，原始数据及最初失败结果均保留。最终按同一冻结时序重算，64组均通过源关联和LTF时序校验；对每组换错误MAC或将候选包TSF偏移10微秒，均被拒绝。

这些是原始相位及未校准诊断角，**不是无人机真实方向，也不是角度误差**。尤其两次开机间相位明显不同，说明目前不能用一次短时标准差代替重复性、准确性或多径鲁棒性。没有把任何本轮相位强制归零。

第三轮实时运行时已触发“图传候选→跳过身份→双站相位／诊断角”，但当时仅放行最先验证的MCS2，其余模式尚在校验；最终MCS 0～5版本已通过上述64组真实数据离线回归并部署。最终部署后无人机保持关闭，没有再要求用户开启第四轮。因此需要区分“第三轮真实实时运行”与“最终扩展版本的离线真实数据验收”，不混称最终版全部模式已再次空口复测。

当前没有有效交汇坐标。软件保留前后模糊候选，两天线不能唯一确定360°方向；没有根据已知摆放位置强行选边、修改相位偏置或制造交点。
